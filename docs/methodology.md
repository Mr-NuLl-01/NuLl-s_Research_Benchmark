# 评测设计、区分度和使用实验

## 设计目的

NRB-10测的是一组科研协作行为：能否使用正确证据和假设，把问题转成结果，再把结果可靠交付。经典热学、线性校准、收缩映射和合成机械测量提供公开、可求解、可检查的载体。任务内容没有取自私有项目；个性化发生在能力侧重与质量标准上。

完整研究没有一个唯一“标准文本答案”。因此v0.2并列记录可精确检查的自动分、需要科学判断的质量分，以及核心责任是否完成。自动检查包括真实代码行为、矩阵/方差计算、约束可行性、具体反例和SVG数据；独立审阅检查推理、边界、实验可行性、实际视觉与英文修订的保真程度。核心证明或交付失败不能由其他得分补偿。

与现有基准的关系是借鉴评测构造，不是复制题目。SciCode把科学问题分解为需要领域知识和实现的子问题，CORE-Bench着重研究结果复现；NRB-10使用更小的可独立运行任务，在这些能力旁加入证据审计、质量审阅与交接。[SciCode官方仓库](https://github.com/scicode-bench/SciCode)；[CORE-Bench原论文](https://arxiv.org/abs/2409.11363)。本版实际阅读范围见[sources.md](sources.md)，不声称完整复现过这些已有基准。

## v0.2切换与结果边界

当前契约为v0.2.0，仍是十个任务家族、每题70自动分加30独立质量分。v0.1的历史提交与验证保留；v0.2修改了数值输出契约、部分生成数据、判断模板、最优层级、行为案例、完成条件及评分身份，不能与旧成绩直接混比。正式运行应固定一个v0.2提交，重新导出无答案题包，并保存评分器commit和实际内容digest。详见[迁移说明](v0.2-migration.md)。

仓库目前的oracle、empty、错误控制、mock与容器验证说明的是程序行为和已测试运行边界，**尚无真实模型的能力成绩或稳定排名**。这些记录不能证明题目已经有多模型区分度，也不能用一次参考程序满分推断模型能够完成研究任务。

## 分数与核心完成同时报告

| 结果维度 | 回答的问题 | 报告方式 |
|---|---|---|
| 自动分 | 哪些可计算/可执行检查通过 | 70分原始值、逐项检查、覆盖率与归一化分 |
| 独立质量分 | 推导、解释、视觉、文字和交接质量如何 | 三项各0–10；未审保持null，模型辅助审阅标provisional |
| 核心完成 | 必需成果、执行和科学责任是否成立 | `complete / failed / pending_review / infrastructure_unscored`，同时列关键失败与待评项 |
| 操作性可用门槛 | 达到预先冻结的分数门槛且核心完成了吗 | `quality_qualified=true` 要求核心complete且完整总分≥80；未知为null |

80是预设操作门槛，尚未通过真实模型校准。原始总分不因核心失败暗中改写：例如NRB08自动70、质量0/0/10但两个证明缺失，仍记总分80，同时记核心failed。正确成果若总分不足80，也可为complete但未达到可用门槛。没有评阅不能假定证明通过；执行环境不可用也不能伪装成候选答错。

NRB03实际调用 `solve(problem)` 的复现属于必经核心执行责任，**新增自动分为0**；数值答案得70并不足以完成。NRB04/05继续各有50分候选代码行为检查。NRB09静态数据检查之外需要独立实际渲染、查看整图与180mm等效展示并核对科学含义。三个执行/视觉责任都应保留实际证据，不能由候选自称“运行成功”替代。详见[评分规范](scoring.md)与[harness流程](harnesses.md)。

## 区分度怎样设计

题目中同时存在直接计算、条件判断和跨步骤整合，避免满分只取决于长文本。

| 机制 | 在题目中的具体实现 | 应区分的失败方式 |
|---|---|---|
| 相似材料需要不同判断 | 更正/旧版、原始/二次、独立/重复采样 | 总结流畅却采用错误来源 |
| 更多数据未必增加信息 | 热系统尺度等价与已知附加热容 | 拟合成功就认定参数唯一 |
| 局部漂亮答案不满足整体条件 | minimax目标、未知截距、多项整数约束 | 报出好目标值却交了不可行设计 |
| 正例之外必须守住不变量 | 非均匀单元能量收支、接口热阻 | 只过示例，换网格就失效 |
| 失败过程也是输出的一部分 | 拒步回滚、最小步长、终点 | 只看终值，状态已被失败尝试污染 |
| 很小的单位差会改变结论 | PSD与ASD、协方差、部分通带 | 返回量纲错误或全零也“接近” |
| 数据顺序和统计单位可误导 | 打乱row_id、机器级split、整组bootstrap | 行级随机划分、看测试选模 |
| 证明对象不能被偷换 | 加权范数与普通范数、谱半径反例 | 把正确定理条件换成更弱条件 |
| 文件里的内容才是交付 | 核对SVG实际坐标、真实字节hash | JSON里数字正确，图或文件错误 |
| 证据状态必须改变判断 | 当前/旧revision、通过/失败/未运行/不足及完整证据变体 | 宣称全面PASS、机械地一律否定或擅自强化结论 |

这些是**预期区分机制**。参考程序满分、错误变体失分只说明评分器能区分已构造控制，不能证明前沿模型之间已有显著差距。真实区分度需要多模型、重复运行和独立评分。

## 三类运行条件

### 固定输入的模型测试

只提供完整题包文本，不提供shell或外部检索工具。模型可以写出代码/图的文本，由外部评分器执行或核验。Inspect的默认solver和promptfoo的普通provider属于这类。结果更接近指定提示和输出预算下的模型能力。

### 可使用工具的agent测试

同一题包放进新容器，agent可查看文件、编写/执行代码和生成图。模型版本、harness版本、工具、skills、多agent开关、自动压缩/恢复策略与预算一起构成被测系统。Harbor导出支持agent与评分器分别运行，默认不生成oracle `solution/` 且agent执行阶段无网络；在线API需显式固定精确host白名单，并关闭provider服务端搜索。通用CLI bridge可接现有工具，但单纯新建工作目录不是安全隔离；本机运行默认标成diagnostic。`--execution docker`只隔离提交代码的评分执行，不隔离生成答案的CLI进程。候选不能挂载评分仓库、旧日志或答案，具体步骤见[避免答案访问](testing-without-answer-access.md)。

### skills与工具消融

在相同模型、harness、题目、预算和seed下，只改变一个预先声明的因素：例如无skills/固定公开skills、单agent/多agent、无执行/可执行。必须记录skills内容hash。不得把本仓库题目答案或针对本题定制的解题脚本放进候选skills包。跨不同工具条件的差值应解释为系统条件的影响，不能直接称为基础模型提升。

实时资料检索可作为独立的补充实验，但不混入封闭资料主分数。本版NRB01所有证据均已给出，它评价检索后的来源判断与阅读。真实论文可访问性、搜索排序和内容漂移会引入另一类变量，需要另立带日期的来源冻结与人工证据审计协议。

## 推荐实验矩阵

先完成不调用模型的selftest、隔离检查及执行/渲染冒烟测试，再安排真实模型试跑。NRB03搜索、NRB04/05候选行为与NRB09渲染分别保留回执；自检不计入实验矩阵。下面是待实施的实验建议，不是已完成的模型测试。

1. **快速诊断**：同一个配置，seed=0，10题，每题1次。目的是暴露主要薄弱环节，不给稳定排行榜结论。
2. **配置筛选**：2个模型 × 2个harness条件，固定seed=0，每题各3次。得到4个完整的系统配置，不把条件差异掩盖成一个“模型名”。
3. **稳健对比**：每配置10题 × 3个数据seed（例如0、17、101） × 3次独立会话 = 90个尝试。预先固定全部预算与失败重跑规则。90个尝试仍然只是10个任务家族。

v0.2 的证据状态校准需额外保证覆盖：NRB10的seed0–7覆盖八种语义状态；上面的0、17、101适合数值/接线自检，并不覆盖所有证据状态。评估“一律回答检查未完成”是否仍能投机时，应预先选择包含完整证据与不同缺失/失败情形的平衡seed集，例如先用0–7做开发诊断，再冻结新的同等覆盖集合。增加seed没有增加独立任务家族数，所有比较对象用同一集合。

每个题包的task seed控制输入；模型sampling seed（如果provider支持）单独记录。重复运行不要复用聊天记忆、工作目录或旧答案；跨配置可以配对使用相同任务seed，但不能在看到失败后仅给某个模型额外修改机会。顺序随机化，避免服务负载和先后顺序系统性偏向某个配置。

时间和token上限不必永远固定为某个数字。建议先使用10–15分钟每题、足以容纳完整代码/图的输出上限作为试跑配置；一旦开始比较就冻结。推理模型的内部思考token与可见输出token统计方式可能不同，所以同时记录原始provider usage、墙钟时间与实际成果。

## 怎样分开模型与harness影响

设同一模型M在两个harness下的分数为S(M,H1)、S(M,H2)，它们的配对差估计这个任务集合与预算下的系统差异。固定H比较M1/M2才比较模型变化。若四个组合都跑，检查两个模型对harness的收益是否一致；若不一致，不应给出一个适用于全部模型的harness排序。

harness能力包括读取正确文件、维持任务状态、实际调用工具、从错误恢复和交付完整文件。评分器只直接测最终成果和已记录的运行事实，并不因为某模型自称“调用了工具”就奖励它。原生runner记录输入hash、命令、时间、退出、输出、usage（如果可得）和输入是否改变。更细的工具轨迹从各harness原生日志审计，不伪装成已经统一实现的全轨迹评分。

## 汇总、比较与不确定性

先对每题家族内的seed和重复求均值，再对10家族等权平均。套题汇总保留十题分母，缺题、失败、基础设施未评和待审题不能消失。除原始分与配对分差，还应报告 `task_table`、核心完成/失败/待审/基础设施未评数量、关键失败率、待评题数和最低题分。有未知状态时，完成率和关键失败率报告上下界，不仅对已评题计算比例。

`nrb compare`要求成对运行使用相同task/seed、相同输入hash、完整自动评分，以及完全一致的benchmark版本、evaluator commit和digest。汇总和比较先验证自动/已审报告封存、分数明细与完成状态，避免事后改动某个总分或完成标签。其bootstrap以家族均值为单位，避免把种子变体误当成独立学科。

默认比较自动归一化分。诊断模式允许保存元数据缺项，但会明确列出限制：

```bash
python -m nrb compare \
  --a reports/A-s0-r1.json reports/A-s17-r1.json reports/A-s101-r1.json \
  --b reports/B-s0-r1.json reports/B-s17-r1.json reports/B-s101-r1.json \
  --score-kind automatic --mode diagnostic --out reports/A-vs-B-auto.json
```

完整质量总分采用显式的reviewed口径；三项质量分必须齐全且总分存在，核心完成状态仍另外展示：

```bash
python -m nrb compare \
  --a reports/A-reviewed-s0-r1.json reports/A-reviewed-s17-r1.json \
  --b reports/B-reviewed-s0-r1.json reports/B-reviewed-s17-r1.json \
  --score-kind reviewed --mode controlled --out reports/A-vs-B-reviewed.json
```

| 模式或身份 | 接受条件及限制 |
|---|---|
| `--score-kind automatic` | 默认口径，比较自动分/70的百分值，不把30分审阅补满 |
| `--score-kind reviewed` | 要求已填写并绑定的质量审阅及完整总分；不把有总分等同于核心complete |
| `--mode diagnostic` | 可保留模型、工具、预算等元数据缺项，逐项列出；不据此建立受控排名 |
| `--mode controlled` | 要求明确的受控轨道、精确模型/harness版本、工具策略、skills、推理、预算、隔离及evaluator commit信息；必经执行不能未评 |
| 相同的元数据缺项 | 两边都不知道模型版本或预算，仍然是缺失；不能因此满足controlled条件 |
| 旧版或缺身份报告 | 可按 `legacy_unverified` 读取历史记录，不补成当前身份，不能进入compare |
| 不同评分身份或协议无效 | 拒绝混比；评分修订后统一重评并保留原报告 |

受控已审比较还要求一致的审阅来源条件，不能把人工与LLM审阅混成同一裁决标准。LLM辅助结果和人工/LLM混合汇总保留provisional标签。两位独立盲评者可检查评分一致性；遇到核心科学分歧，保留分歧与人工裁决记录。review ledger绑定题包、原提交、量表、审阅政策、评分器身份与自动报告hash，改变交付或评分后必须重建相应审阅。

这些区间只描述选定家族和配置下的差异，不是“全部科研能力”的总体置信区间。量表尚未校准、任务数量少、题目并非独立抽样等限制仍然存在。分数接近、关键题方向相反或人工评分分歧大时，应报告尚不能稳定排序。

效率需与质量和完成同时看。快速失败不能称为高效率；可报告达到预先定义可用标准的任务比例、这些任务的时间/费用，以及所有失败尝试累计费用。provider未提供token或价格时保留缺失，不自行猜估。无论自动分多高，执行未评、证明失败和无意义交付都应在效率表旁可见。

## 抗污染与维护

公开源码支持可审计性，也意味着任何公开答案都可能进入模型训练或被agent搜到。随机seed只能减少直接记忆具体数字；如果生成器和解法公开，它不能证明不存在污染。应使用运行前才生成的seed、新候选环境、禁读评分器/参考目录与必要的网络政策，仍如实披露公开基准的限制。

最优策略不是不断叠加罕见措辞或人为陷阱。先检查真实分差集中在哪些责任；若强模型普遍满分，可在同一家族增加有科学意义的新条件、更真实的数据质量问题或更长的依赖链。任何条件/数据/评分变更都形成新版本，保留旧版可复跑。不因模型给出另一种正确方法而修改题目阻止其得分。

v0.2完成契约和程序控制后，下一阶段仍是真实校准：至少两个能力层级的模型、多次运行、两位盲评者、错误归因与评分一致性分析。正式试跑使用全新上下文和无答案题包，不将修改方案、参考解或负控制送给候选。只有完成这些步骤后，才把“设计上应有区分度”升级为“已测得哪些区分度”。
