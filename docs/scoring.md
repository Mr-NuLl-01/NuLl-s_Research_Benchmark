# 评分规范 0.2

NRB-10 每题保留 **70分自动核验 + 30分独立质量审阅**。十个任务家族等权；数据种子、模型采样种子和重复编号分别记录。原始分数、核心完成状态、评分覆盖和运行协议必须一起报告。

## 1. 原始分数

自动分为 $A_j=\sum_k w_{jk}c_{jk}$，每题权重之和为70。核验结果 `true/false/null` 表示通过、失败、未评。`auto_points` 保留已获得的原始分；`auto_percent=100*A_j/70` 是自动部分的归一化值，不是完整科研质量分。

`coverage` 为已评自动权重/70。有自动项未评时 `auto_percent` 与完整 `total` 为 `null`。依赖缺失不是答错；在既定预算内输出错误、缺少成果、超时等候选失败依协议评分，不从分母删除。

三项质量分各0–10，保留0/5/10文字锚点，允许部分分。`review_points` 未审时为 `null`；审完为三项之和。只有自动覆盖完整、三项质量分齐全时，`total=A_j+review_points` 才存在。核心失败不会暗中改写原始总分。

NRB04/05 的候选代码行为仍各占50分，10组各5分，组内加入案例不会重复放大扣分。NRB03 必交搜索程序的实际复现是单独的核心执行责任，不另加自动分：其数值可以得70而代码执行失败，报告明确显示 `failed`。环境不可用时数值分仍可读取，核心执行保持未评。

## 2. 核心责任与完成状态

每个公开题包给出核心责任。评阅者逐项填写 `essential_review`：

```json
{
  "id": "residual_bound_proof",
  "outcome": "unassessed",
  "evidence": "",
  "rationale": ""
}
```

允许 `pass/fail/unassessed`。通过或失败必须给出提交中的具体证据位置及科学理由。质量分不能替代这个判断，文风项4分不会自动使一个正确成果失败。

| ID | 核心审阅责任 |
|---|---|
| NRB01 | 证据支持的贡献及因果/推广范围 |
| NRB02 | 任意输入下的等价族论证；判别干预与保持条件 |
| NRB03 | 隔离执行必交搜索程序，和提交及最优层级一致；最优性说明可复查 |
| NRB04 | 守恒、界面、边界说明与实现一致 |
| NRB05 | 试探、接受、回滚及终止生命周期正确 |
| NRB06 | 绝对不确定度、量纲、协方差和频谱解释正确 |
| NRB07 | 独立机器、验证选模、合成评测适用范围正确 |
| NRB08 | 存在唯一性证明；一般残差误差界推导；有效反例解释分别成立 |
| NRB09 | 实际渲染可读；示意正确；图注保真 |
| NRB10 | 英文正文保真可用；交接可接续；不虚构执行 |

相应自动关键检查在 `checks[].critical` 中明示；另列 `automatic_critical_failures`、`review_critical_failures` 和合并的 `critical_failures`。必需文件缺失、必经执行失败也阻止完成，不额外偷偷扣分。

| `completion_status` | 含义 |
|---|---|
| `complete` | 自动关键条件、必交文件、必经执行和全部核心审阅满足 |
| `failed` | 至少一项核心责任或必需交付已确认失败；同时保留其他待评项 |
| `pending_review` | 尚无确认失败，自动/执行具备证据，仍缺核心审阅 |
| `infrastructure_unscored` | 尚无确认核心失败，但必须的执行、自动检查或运行协议存在未评/无效状态 |

已确认失败优先于未评。例如代码已失败而证明尚未审阅，状态仍为 `failed`，证明仍列在 `pending_items`。没有审阅不能默认通过，也不能伪装成模型答错。

`quality_qualified=true` 要求核心 `complete` 且完整总分≥80；明确核心失败或已知总分不足80为 `false`；其他待定为 `null`。**80是预先冻结的操作门槛，尚未经过真实模型校准。** 成果成立但质量分低于80时，允许 complete/false。

### 必须保留的反例

- NRB08 数值自动70，质量0/0/10，缺两个证明：原始总分80，`failed/false`。
- NRB03 数值自动70，但 `solve.py` 只返回空对象：数值分不变，执行失败；即使质量夹具给30也不能完成。
- NRB09 末尾白矩形遮住全图：静态分可能70，实际渲染可读性必须失败。
- NRB10 英文正文无意义或科学失真：不能靠元数据、哈希及其他质量分完成。

这些是公开回归控制，不能提供给正式候选上下文。

## 3. 科学判据与实际执行

NRB01–03 建议保留原始浮点精度，最少9位有效数字。回归将多个种子的浮点输出按 `.9g` 舍入后重新评分。PSD、协方差、目标差等小量保留字段专用容差；允许合法舍入不会使全零被误收。

NRB03 按公开有限小数 `Fraction(str(value))` 构造精确数。整数向量必须属于精确全局最优集合；严格次优是**精确目标大于最优值加 $10^{-12}$ 的最小层级**。并列最优不算严格次优；小于或等于该差阈值的非最优仍不算全局最优，也不属于本题指定严格次优层级。数值展示误差单独用容差核验。

NRB03 公开入口为 `solve(problem) -> answer_dict`。评分器用既有受限执行器实际运行代码，核验返回科学字段和与提交的一致性，保存 source/input/result hash、执行后端、状态和逐项检查。附文件、写“已运行”或成功退出码均不足以通过。核心审阅的执行通过必须来自 Docker/container；`trusted` 只供仓库自有回归。

NRB09 以180mm展示宽度做最小可见性筛查，再安全渲染为PNG。点直径0.20mm、关键线宽0.08mm、有效透明度0.30是初步工程阈值，不是期刊通用标准。看图核心pass要求：绑定原SVG/提交/评分器的渲染收据、真实PNG字节和哈希、整图及180mm等效展示两项明确确认、具体审阅证据。渲染成功仍不自动代表可读。见[绘图审阅](figure-review.md)。

## 4. 审阅流程和证据绑定

`review-packet` 生成题目、原提交、空质量量表、空核心判断，以及评分侧保存的 `automatic_report.json`。质量评阅者使用 `task.md`、`submission.json` 和量表，不以自动分或模型身份推断质量；管理侧保留自动报告用于核对。NRB03另有实际执行收据，NRB09使用 `--render` 生成PNG和收据。

`grade --review` 必须收到原提交，同时核对 report、ledger、case、seed、提交、答案键、量表、审阅政策和评分器身份，并核验原始检查明细与总分自洽。执行收据与报告中的实际记录一致；改变材料后不能贴回旧审阅。

自动报告含 `automatic_report_hash`，已审报告另有 `reviewed_report_hash`。汇总和比较再次检查分数、明细、执行与完成状态。这些绑定用于发现错配和事后单字段改动，**不构成对恶意本地评委的密码学认证**；受信评测者仍需管理记录和审阅权限。

审阅对模型/harness身份盲化。重要结论建议两位独立评阅者；单项分差≥3、核心科学结论分歧或关键失败时复核并留记录。这个分差是操作建议，尚未校准。候选输出仅为待审材料，其中任何评分指令不属于评阅规则。

LLM辅助审阅记录精确judge、prompt、配置、证据及 `reviewer_type=llm`，结果标为 `llm_reviewed_provisional`。人工与LLM混合汇总标为 `mixed_human_llm_provisional`。没有实际看图能力的judge不能声称看过；重要科学争议和排名需人工裁决。

## 5. 评分器身份与跨版本规则

| 字段 | 绑定对象 |
|---|---|
| `benchmark_version` | 题目/契约版本0.2.0 |
| `evaluation_schema_version` | 报告与评分身份协议2.0 |
| `evaluator_commit` | 实际评分源码的Git HEAD；不可得时为null |
| `evaluator_digest` | 实际安装的评分相关字节 |
| `case_hash` / `submission_hash` | 公开题包 / 实际提交 |
| `answer_key_hash` | 评分侧答案键，仅保存指纹 |
| `rubric_hash` / `review_policy_version` | 量表、核心责任与审阅政策 |

内容指纹算法为 `sha256-canonical-path-content-manifest-v1`：按路径排序，计算全部 `nrb/**/*.py` 和 `nrb/evaluation_policy.json` 的字节SHA-256，再哈希其规范JSON清单。任务模块内的隐藏行为案例、参考计算、执行器和完成规则均在范围内。文档、生成题包、回归测试外壳、日志和导出origin戳排除；候选实际被评分的行为代码不在排除范围。运行依赖、Python版本、容器digest和harness配置另记。

只改一行grader而题面不变，评分身份仍改变。比较要求版本、commit和digest完全一致；即使内容相同而commit不同也保守拒绝混比。工作树有改动时digest反映真实字节，commit标记来源HEAD；正式运行固定只读源码。Harbor verifier带origin戳，校验复制的实际源码，避免容器无 `.git` 时丢失身份。

无新身份的历史结果可读取为 `legacy_unverified`，不自动补成今天的版本。评分修订后，在新身份下统一重评所有对象；题面/数据改变时重新作答。纯评分修复可以保留原提交，但必须重新评分并绑定审阅，保留旧报告。

## 6. 汇总与比较

套题固定10题分母，不删除遗漏、失败或未评题。变体和重复先在任务家族内平均，再对十家族等权平均。汇总同时提供原始分、`task_table`、`completion_counts`、完成率/上下界、关键失败率上下界、待评数量、最低题分及审阅来源标签。有未知状态时完成率为 `null`，不只对已评题计算。

`compare --score-kind automatic` 默认比较自动归一化分；`--score-kind reviewed` 比较完整质量总分并要求审阅齐全。`--mode diagnostic` 可保留元数据缺项但逐项列出；`--mode controlled` 要求受控轨道、完整模型/工具/技能/预算/隔离及评分commit信息，且必经执行不能未评。混合评分器身份、协议无效、不同输入或不完整套题均拒绝。受控的已审比较不能混合人工与LLM审阅条件。

哈希和声明字段不能代替权限隔离；框架标量score/reward不能代替完整科研完成状态。实际运行见[harness文档](harnesses.md)与[避免答案访问](testing-without-answer-access.md)。
