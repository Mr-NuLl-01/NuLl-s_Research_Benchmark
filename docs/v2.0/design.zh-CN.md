# NRB 2.0 第一轮：题库与评分设计

版本：`2.0.0-rc.1`。日期：2026-10-23（中国标准时间）。

本轮交付范围是 **8 道 Python 客观题、对应自动评分器、网页操作流程及 Google Drive 下载入口**。完整题库按 20 题组织；其余 12 题属于第二轮规划。当前版本不是“20 题均已完成”的正式发布。

## 1. 先解决评测流程中的实际问题

原 V1.1 的科学编程题使用“自动 70 分 + 人工 30 分”，即使代码通过，仍需要人工填写说明质量、测试质量和核心责任。网页又允许直接录入总分草稿，未真正运行同一评分器。这会造成三个混淆：提交了代码是否等于完成；录入的总分是否由检查得到；自动测试通过后为什么仍显示待评。

新 Python 协议只要求 `solution.py`，使用统一的 `solve(problem)` 接口。说明、自测代码可以一并提供，但不产生人工分，也不阻断自动完成。验证器实际执行程序，保留所有检查结果，并把自动权重归一化到 100 分。网页导入本地报告，检查发行版本和检查清单，重新核算分数；它会明确说明报告来自本地执行。

程序是否满足全部检查，与部分分数同时报告。例如一个程序获得 90 分但仍有一项失败，应显示“90 分，未全部通过”，而不是仅依据 80 分阈值判定完成。环境无法执行时分数为空；不能把缺少 Docker、依赖不可用或未运行当成模型的 0 分。

## 2. 八道 Python 题与能力区分

保留现有题目中已经具体化的科研问题，而不为更新而重造八个相似的数值练习。下列难度是设计先验，尚未用不同模型的真实成绩进行统计标定。

|---|---|---|---:|---|

|P02|C02|独立组与分层 bootstrap 模型比较|2/5|统计单位、组权重、层权重、确定性重采样；把测量行当独立样本会失败|

八题统一允许标准库、NumPy 2.3.5和SciPy 1.17.0；旧后三题的“仅标准库”限制不再保留。评分重点是科学计算合同，不能靠题面禁止但环境允许的依赖形成未执行的人工约束。固定库版本不改变P02随机流、P05积分推进及其他明确算法要求。

难度并非只由程序长度决定。P01/P02 主要区分是否准确理解数据语义；P03/P04/P07 进一步区分物理公式和离散实现；P05 检验算法状态机；P06 检验反演边界；P08 检验多个模块联动。相同的“4/5”也有不同失败机制，应展示逐题能力图谱，不能仅用均分替代它们。

### P01：基础题仍要区分科学数据语义

温度单位为 K、C、mK，误差是已知标准不确定度。题目明确重复键由最后一条可用记录覆盖；跳过行不能清除已有可用值。均值与标准误使用独立测量不确定度，而不是用样本标准差代替。极小合法 sigma 要求稳定权重缩放，不能仅测通常量级。

### P02：统计单位比库函数选择更重要

先在组内归约，再在层内与层间按合同加权。随机数算法、遍历顺序和分位数定义在题面公开，所以这里可以要求精确重现指定的重采样结果。这是一道明确的统计计算合同题；不能把它解释为“所有合理 bootstrap 都应生成同一随机轨迹”。

### P03：修复必须维持离散能量收支

题内提供有错误的起始实现。非均匀宽度、分层材料、边界条件和源项共同构成错误定位。测试不仅比较最终温度，还检查边界能量与源项累计。靠改最后一行、截断异常值或者在输出中伪造能量账本不能完成任务。

### P04：光学稳定性与边界约定同时测试

模型限于题面规定的平面、各向同性、非磁性被动层。入射/出射半空间为无损介质；p 偏振的振幅约定、纵向波矢分支与能流比明示。允许稳定递推或等价算法；不强制使用会在极厚吸收层中溢出的普通传输矩阵链。独立核对覆盖单界面/无损守恒/厚吸收极限和不同算法的多层结果。

### P05：它测试规定算法，而非任意 ODE 解法

这题明确规定后向 Euler 全步与两个半步的误差估计、取半步解、拒步回滚、步长因子、硬停点及计数方式。因此步数检查属于题意。若题目只要求连续方程解，就不应把某个参考积分器的内部步数当标准；本题必须在题面保留这一限定。局部容差也不等于全局误差证书。

### P06：修正评分参考的边界缺口

V1 参考搜索存在已知边界问题：内部最小值靠近搜索端点时，网格局部极小检测可能只保留端点，漏掉合法内部解。本轮使用独立的 V2 模块修正，并保留原 V1 文件作为历史。测试要证明此修复确实捕获端点邻域解，而不仅是重新执行相同错误参考。

### P07：残差应从候选状态重算

不能只相信候选返回的 `residual_inf`。验证器按候选解重建题面离散算子和边界通量，检查实际残差。实际使用的硬阈值需公开在题面，避免让未声明的判据造成误拒。

### P08：跨模块错误需要真实联动验证

反演、前向求解、离散灵敏度、协方差和 bootstrap 不能分别返回看似合理但不一致的量。重启等价要求本实现按同样运算经过 JSON 往返后精确续接，不要求不同合法算法跨实现逐位一致。

## 3. 自动评分合同

八题的历史自动检查权重每题合计 70；本轮保留这些有意义的相对权重，计算：

\[
\text{score}=100\,\frac{\sum_i w_i\mathbf{1}(\mathrm{passed}_i)}{\sum_iw_i}.
\]

原三组权重 20、30、20 对应新百分制约 28.57、42.86、28.57。报告保留原权重及每组得分，避免显示舍入累积。题目之间等权；八题完整成绩是八个百分制分数的算术平均。

只有所有检查都被评定后才有完整分数。若有未评定检查（`passed=null`），整体分数保持 `null`；环境不可用不记0分。语法/接口错误、错误返回和数值不满足属于候选失败。候选进程整体超过程序运行时限时，整次调用按预算违约判失败，所有检查记失败并计0分，不称为环境未运行。这个执行时限与模型的作答预算是两回事；编译器/容器不可用则不代表候选能力失败。

每条报告绑定题号、题库版本、种子、题包指纹、检查清单指纹、评分器内容指纹和候选源代码指纹。当前网页支持种子 0、17、2026 的发行清单；默认 17。不同版本不能直接混入同一汇总。

### 数值比较

浮点字段使用各题明确的绝对/相对容差，并检查形状、有限性与 JSON 类型。布尔值不能冒充数字，NaN/Infinity 不合格。整数计数和状态按合同精确比较。不能使用一个宽泛的默认 `allclose` 处理所有量级；NumPy 官方也明确提醒默认绝对容差不适合远小于 1 的量。[4]

### 自测与真正的模型测试

正确参考、故意错误实现、空输出与超时控制用于检验评分器是否工作；它们不属于模型成绩。只有在固定模型版本、工具、skills、推理强度、预算和尝试规则后，实际让模型作答并独立评分，才能形成模型比较。

发布的评分器和测试可以被下载，因此不是保密测试。个人闭卷使用时只把单题候选文件交给模型；评分端另外保存验证器。未来公开排行榜需要另行设计受控执行、独立未公开参数和成绩真实性机制，不把这些尚未实现的能力写进当前产品。

## 4. 网页与本地评分器的分工

主要路径为：题库 → 题目详情 → 获取单题材料 → 模型作答 → 本地验证 → 导入报告 → 查看检查 → 保存/比较。

网页不能仅解析一个 `score:100` 就声称完成验证。它以发行清单核对题号、版本、种子、所有检查 ID、权重与关键项，从检查结果重算总分；缺失、重复、非法类型或不一致汇总明确报错。普通 JSON 与 SHA-256 都不是签名，因此界面称“本地报告导入”，不称“服务器认证通过”。

程序题入口不提供人工总分框。直接上传 `solution.py` 时，应给出本地验证的具体操作和正确文件类型，而不是吞掉输入。主观题与另外两道 chat 题在本轮只展示计划，避免让未完成的量表假装可用。

详情页有明确返回入口。筛选、空结果、关闭详情、保存成功/失败、导入错误与下一步均有反馈。旧 V1 记录与原题保留为历史；不得自动改名成新版本成绩。旧记录继续使用原浏览器存储键，升级过程不覆盖或静默删除。

## 5. Google Drive 下载策略

题面、候选包和验证器通过实际上传并读取元数据确认的 Google Drive 文件链接提供。网页打开 Drive 的正常授权页面，不通过前端跨域 fetch 私有文件，也不依赖临时签名下载接口。

下载资源清单记录文件名、大小、SHA-256、Drive 文件 ID 和可访问链接。文件延续私有权限；用户通过自己的 Google 账号下载。原视频 A/B 包保持已有链接和权限，第二轮合并时再发布新合同。

记录导出是浏览器中的本地备份操作，仍直接保存 JSON；它不是题库下载接口。记录本身不自动上传 Drive，也不作云同步。资源清单中的 Drive 链接不代表公众可访问。
